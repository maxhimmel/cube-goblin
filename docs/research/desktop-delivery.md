# Desktop delivery (signing, updates, icon): research

Researched 2026-11-16. Context: get the Electron app ([desktop-shell.md](desktop-shell.md)) onto one friend's machine. Packaging basics, fuses, and the unsigned `--mac dir --arm64` spike live there; this covers what comes after. Versions from `npm view` that day: `electron-builder` 26.18.0 (`latest`; a `v26` tag already has 26.18.1), `electron-updater` 6.8.11. "Checked in tarball" means the `app-builder-lib@26.18.0` / `electron-updater@6.8.11` npm packages.

## Platform state

- **Current macOS is 27** ("Golden Gate"): 27.0 shipped 2026-09-14, 27.2.1 on 2026-11-09 ([releases](https://developer.apple.com/news/releases/)). This Mac runs 15.7.2.
- **Intel is ending**: macOS Tahoe 26 is the last release for Intel Macs, and Rosetta for apps ends after macOS 27 ([26.4 notes](https://developer.apple.com/documentation/macos-release-notes/macos-26_4-release-notes)). Settings in 27 already lists Intel apps that won't run on 28 ([27 notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)).

## macOS without a Developer ID

- **Apple Silicon won't run unsigned code**: every arm64 executable needs a signature, but an ad-hoc one is enough. Rosetta x86 binaries are exempt. Ad-hoc signatures aren't tied to the build machine and verify anywhere, but they "cannot pass through Gatekeeper" ([Big Sur universal apps notes](https://developer.apple.com/documentation/macos-release-notes/macos-big-sur-11_0_1-universal-apps-release-notes)). That corrects desktop-shell.md's "runs only on the build machine". Electron's own docs say an unsigned or ad-hoc app "may behave inconsistently" ([code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing)).
- **What our build is today**: Electron 45.3.2's prebuilt `Electron.app` and `Electron Framework` are ad-hoc linker-signed with no Team ID (`codesign -dv`, 2026-11-16). After the fuses are flipped, `resetAdHocDarwinSignature` re-signs ad-hoc, but `codesign --verify --deep --strict` on `release/mac-arm64/*.app` fails with "a sealed resource is missing or invalid" in `Electron Framework.framework`. A build with `-c.mac.identity=-` passed the same deep check. A broken seal risks the "app can't be opened … damaged" path instead of "Open Anyway" ([Safely open apps](https://support.apple.com/en-us/102445)); not yet tested on a real download.
- **`identity: "-"` in 26.18**: opts in to ad-hoc signing. Unset with no certificate means no signature at all; there's no automatic ad-hoc fallback. With the default `hardenedRuntime: true` it also needs `com.apple.security.cs.disable-library-validation`; otherwise set `hardenedRuntime: false` (schema `mac.identity`/`mac.hardenedRuntime`, checked in tarball; [code-signing-mac](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/code-signing/code-signing-mac.md)). Fuses are flipped before signing (`doAddElectronFuses` then `doSignAfterPack` in `macPackager.js`), so with any signing on, `resetAdHocDarwinSignature` is unneeded. The schema says the same.
- **Gatekeeper, macOS 15+**: Control-click → Open no longer bypasses Gatekeeper for software that isn't signed correctly or notarized ([Apple news, 2024-08-06](https://developer.apple.com/news/?id=saqachfa)). The friend opens the app once, then goes to System Settings → Privacy & Security → Open Anyway, enters an admin password, and confirms. The button shows for about an hour after the failed open, and the app is then saved as an exception ([Mac User Guide](https://support.apple.com/guide/mac-help/open-a-mac-app-from-an-unknown-developer-mh40616/mac), version picker covers 27; [Safely open apps](https://support.apple.com/en-us/102445), 2026-05-27). The 26 and 27 release notes list no Gatekeeper UX change; 27 adds `spctl --purge` ([27 notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)).
- **`xattr -dr com.apple.quarantine "/Applications/<App>.app"`**: strips the download mark recursively (`-d` delete, `-r` recurse; `man xattr`), so the first-launch check for downloaded software doesn't fire ([Gatekeeper](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web)). It skips the Settings dance but means a Terminal step for the friend. Inferred from the docs; not tested from a real download.
- **Local simulation doesn't count**: setting `com.apple.quarantine` by hand on this Mac and running `open` launched the app through App Translocation with no prompt. Prove the friend's flow by downloading on a second Mac.
- **Arch**: `--arm64` covers every Apple Silicon Mac. `--x64` only matters for an Intel Mac (which tops out at macOS 26), and Rosetta ends after 27. `--universal` merges both, and electron-builder says it works best when both arches are built natively ([mac.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/mac.md)).

## Developer ID + notarization

- **Program**: 99 USD per membership year. An individual needs an Apple Account with 2FA and their legal name. An organization needs a D-U-N-S number, a domain email, and a website ([enroll](https://developer.apple.com/programs/enroll/)). Only the Account Holder can create the Developer ID certificate ([Developer ID](https://developer.apple.com/developer-id/)).
- **Notary prerequisites**: a Developer ID Application certificate, hardened runtime, a secure timestamp, and no `get-task-allow`. Once the ticket exists, Gatekeeper finds it online or stapled ([notarizing](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution); [hardened runtime](https://developer.apple.com/documentation/security/hardened-runtime)).
- **Certificate inputs**: `CSC_LINK` takes a `.p12` as a path, URL, or base64. Also `CSC_KEY_PASSWORD` and `CSC_NAME` (macOS keychain identity name). On a dev Mac, a keychain identity is picked up automatically. Signing a Mac app works only on macOS ([code-signing](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/code-signing/code-signing.md), [multi-platform](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/multi-platform-build.md)).
- **Notarize trigger in 26.18**: `mac.notarize` is boolean only, and `false` disables it. Otherwise notarization runs after signing whenever one env set is complete (`getNotarizeOptions` in `MacTargetHelper.js`, checked in tarball):
  - `APPLE_API_KEY` + `APPLE_API_KEY_ID` + `APPLE_API_ISSUER`: the schema recommends this one.
  - `APPLE_ID` + `APPLE_APP_SPECIFIC_PASSWORD` + `APPLE_TEAM_ID`.
  - `APPLE_KEYCHAIN_PROFILE`, optionally with `APPLE_KEYCHAIN`.
  - `APPLE_API_KEY` must be a file-system path to the `.p8`, per `@electron/notarize` 2.5.0 types. The electron-builder notarization doc's "base64-encoded p8" is wrong for this version ([notarization.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/code-signing/notarization.md)).
- **Entitlements**: with no `build/entitlements.mac.plist`, the bundled default applies: `allow-jit`, `allow-unsigned-executable-memory`, `disable-library-validation` (`templates/entitlements.mac.plist`, checked in tarball). `hardenedRuntime` defaults to `true`.
- **Our config delta**: drop `mac.identity: null`, `hardenedRuntime: false`, and `resetAdHocDarwinSignature`. Signing now reseals after the fuses, and OS signature checks keep the fuses from being flipped back ([fuses tutorial](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/tutorials/adding-electron-fuses.md)).

## dmg vs zip

- **`dmg`** is for consumer downloads; **`zip`** is what update servers use. The default mac targets are both ([mac.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/mac.md)). `dir` is never signed or notarized there.
- **electron-updater needs the zip**: `MacUpdater` picks the `zip` from `latest-mac.yml` and throws `ERR_UPDATER_ZIP_FILE_NOT_FOUND` without one (checked in tarball). The auto-update doc lists "macOS: DMG" as the updatable target, but its own note says the zip is required ([auto-update](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/auto-update.md)). Ship both: the dmg for first install, the zip for updates.

## Auto-update (electron-updater)

- **How it works**: the build writes `latest-mac.yml` (`latest.yml` on Windows) plus `app-update.yml` inside resources. Don't call `setFeedURL`. Providers: GitHub Releases, S3, DigitalOcean Spaces, Keygen, and generic HTTPS; with generic, you upload the files yourself ([auto-update](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/auto-update.md), [publish](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/publish.md)).
- **Private GitHub repo**: needs `GH_TOKEN` on the user's machine plus `private: true`. The doc calls it "only for very special cases". Each check costs up to 3 API calls against 5000 per hour. Any token shipped in the app is readable by the friend. The repo has no remote yet; a public repo's Releases (or any static host via `generic`) needs no token.
- **Mac auto-install requires a real signature**: "Your application must be signed for automatic updates on macOS" ([autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater); [code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing): Squirrel.Mac "requires the app to be signed … to work at all"). electron-updater downloads the zip, then hands it to native Squirrel.Mac through a localhost proxy (`MacUpdater.js`).
- **Squirrel.Mac's check**: the update bundle must satisfy the running app's designated requirement (`SecCodeCopyDesignatedRequirement` in [SQRLCodeSignature.m](https://github.com/Squirrel/Squirrel.Mac/blob/master/Squirrel/SQRLCodeSignature.m)). An ad-hoc DR is tied to that exact build ([TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)); ours prints `designated => cdhash H"…"`. So every new ad-hoc build fails the check, and ad-hoc auto-update doesn't work. Inferred from the source; not run.
- **Unsigned fallback**: check only. Set `autoDownload: false` and catch `update-available`, then open the download link. Squirrel only gets involved after the download (`MacUpdater.js`).
- **Windows NSIS** updates work unsigned: `NsisUpdater` skips signature verification when `publisherName` is unset (checked in tarball).
- **update.electronjs.org** needs a public GitHub repo and a signed mac build ([updates](https://www.electronjs.org/docs/latest/tutorial/updates)).

## Windows (brief)

- **NSIS** is the default Windows target and the one electron-updater supports; Squirrel.Windows is not supported ([nsis](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/nsis.md), [auto-update](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/auto-update.md)).
- **Unsigned**: SmartScreen shows "Windows protected your PC", and the user must choose "Run anyway". Enterprise policy can block that. Reputation restarts with every unsigned version. On Windows 11, Smart App Control blocks unsigned files that lack reputation. EV certificates no longer skip SmartScreen. Artifact Signing (formerly Trusted Signing) starts at $9.99/month and needs identity validation ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), 2026-05-04).
- **Build from this Mac**: the docs say macOS downloads all needed dependencies automatically, and native dependencies can't cross-compile ([multi-platform](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/multi-platform-build.md)). We have none ([desktop-shell.md](desktop-shell.md#spike-results-2026-11-15)). Verified 2026-11-16: `electron-builder --win nsis --x64` on this Mac, with no Wine, built an unsigned 116 MB `Setup .exe` plus a blockmap. Not run on Windows yet.

## App icon

- **Inputs in 26.18**: `mac.icon` accepts `.svg`, `.png`, `.icns`, or `.icon`, at least 512 and ideally 1024. Search order: the explicit `mac.icon`, then `icon.icns`, `icon.png`, `icon.svg` in `build/` (`buildResources`). SVG is rasterized at 1024. A prebuilt `.icns` is used as-is ([icons-and-images](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/icons-and-images.md); SVG handling in `util/iconConverter.js`, checked in tarball). With no icon, the build logs "default Electron icon is used", as ours did.
- **`.icon` works in 26.18**: it's compiled with `actool` into `Assets.car` plus `CFBundleIconName`. It also produces an `.icns` for `CFBundleIconFile` (`util/macosIconComposer.js`, `macPackager.js`, checked in tarball). The build needs actool 26.0.0+ (Xcode 26+) and macOS 15+; `dmg.icon` still needs an `.icns`. This Mac has only the Command Line Tools (no `actool`), so a `.icon` build fails here until Xcode 26 is installed.
- **Tahoe+ icon rules**: macOS icons are square layers, and the system masks the rounded corners, so don't pre-mask. Icon Composer files get Liquid Glass and the dark, clear, and tinted variants. A bitmap gets auto-segmented into foreground and background ([HIG app icons](https://developer.apple.com/design/human-interface-guidelines/app-icons)). Icon Composer requires macOS Tahoe 26.4+ ([Icon Composer](https://developer.apple.com/icon-composer/)), so it can't run on this Mac.
- **Legacy icons**: "the canvas shape now acts as a mask". An existing icon shaped like the rounded rectangle gets masked or extended. An odd-shaped one loses its drop shadow and is "auto-scale[d] … into our rounded rectangle canvas" ([WWDC25 220](https://developer.apple.com/videos/play/wwdc2025/220/)). The gray plate behind such icons appears only in a developer forum report ([thread 787576](https://developer.apple.com/forums/thread/787576)), not in Apple docs.
- **macOS 15 and earlier don't mask**: full-bleed square art showed as a hard square in Finder and the dmg window on this Mac (15.7.2, observed 2026-11-16). The masking above is Tahoe 26+ only.
- **Practical path**: pre-shape `build/icon.svg`: a rounded square inset on the 1024 canvas with a soft drop shadow (824 px body, 100 px margin, the pre-Tahoe macOS template proportions; not in the current HIG, so unverified against Apple). Tahoe treats an icon shaped like its rounded rectangle as a legacy icon and masks or extends it (WWDC25 220 above). Add a `.icon` from Icon Composer later, on a Tahoe 26.4+ Mac with Xcode 26.

## Options for one friend

Ranked by friction for the friend:

1. **Developer ID + notarized dmg/zip on GitHub Releases + electron-updater.** $99/yr. The friend just double-clicks with no prompts, and updates install themselves. Cost on our side: enrollment, the certificate, an API key, and the config delta above.
2. **Ad-hoc (`identity: "-"`) dmg + zip, shared by link.** $0. The friend clears Gatekeeper once per build, through Open Anyway or the `xattr` line. No auto-install; a check-only "new version" banner is possible.
3. **Current `identity: null` + fuse reset.** $0, but the deep seal is broken, so it risks a "damaged" dialog. Don't ship it.
4. **Windows NSIS unsigned.** $0. The friend clicks "Run anyway" on each new version, and Smart App Control may block outright. electron-updater still works. Signing adds $9.99/mo for Artifact Signing.

**Recommendation**: if the friend has an Apple Silicon Mac, ship option 2 now. That means `identity: "-"`, `hardenedRuntime: false`, targets `dmg` + `zip` for arm64, and a download link. First prove the flow by downloading on a second Mac. Move to option 1 once updates get frequent or the Gatekeeper steps prove too much.
