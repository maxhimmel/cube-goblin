## GitHub Releases and the stable link

- **Documented**: `https://github.com/<owner>/<repo>/releases/latest/download/<asset>` downloads the named asset of the latest release ([linking to releases](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)). Verified 2026-11-16: `cli/cli/releases/latest/download/gh_checksums.txt` 302s to `/releases/download/v2.104.0/gh_checksums.txt`.
- **"Latest" skips drafts and prereleases**: it's "the most recent non-prerelease, non-draft release"; `make_latest` "defaults to true for newly published releases", and "drafts and prereleases cannot be set as latest" ([REST releases](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)). In the UI, unticked "Set as latest" falls back to semver ([managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)). So the share link only moves when a release is published as a full release.
- **Limits**: up to 1000 assets per release, each under 2 GiB, no total-size or bandwidth limit ([about releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)).
- **Immutable releases** (opt-in repo setting): once published, assets can't be modified or deleted and the tag can't move. GitHub recommends draft → attach assets → publish ([immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)).

## electron-builder `github` publisher (26.18)

- **Config shape**: `publish: { provider: "github", owner, repo, releaseType, vPrefixedTagName, tagNamePrefix, private, channel, publishAutoUpdate }` (schema `GithubOptions`, checked in tarball). `owner`/`repo` are otherwise detected from `repository` in `package.json`, then CI env, then the `.git/config` origin ([publish.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/publish.md#github-repository-and-bintray-package)). `apps/desktop/package.json` has no `repository`, so set `owner: "maxhimmel"`, `repo: "cube-goblin"` explicitly.
- **Token env**: `GITHUB_RELEASE_TOKEN` wins, then `GH_TOKEN`, then `GITHUB_TOKEN` (`gitHubPublisher.js`, checked in tarball). In Actions, pass `GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}` ([github-actions.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/github-actions.md)).
- **`--publish`**: `onTag` (tag push only), `onTagOrDraft` (tag push or draft exists), `always`, `never` ([publish.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/publish.md#how-to-publish)). On Actions the tag is read from `GITHUB_REF_TYPE === "tag"` → `GITHUB_REF_NAME` (`getCiTag` in `publisher.js`, checked in tarball). Without `--publish`, 26.x publishes implicitly on CI or when run from an npm script named `release`; it's deprecated and goes away in v27 (`PublishManager.js`). Pass `--publish` explicitly, and don't call electron-builder from a script named `release`.
- **Tag must match the version**: the release tag is `v` + `package.json` `version`; a version starting with `v` throws (`gitHubPublisher.js`).
- **Draft is the default**: `releaseType` defaults to `draft` (schema); `EP_DRAFT` / `EP_PRE_RELEASE` env override it. An existing draft for the tag is reused; a published release older than 2 hours is skipped with "existing release published more than 2 hours ago" unless `EP_GH_IGNORE_TIME` is set (`getOrCreateRelease`). A draft never becomes "latest", so the share link and the update check don't see it until it's published.
- **Recommended for us** (inferred, not run): keep `draft`, then add a last workflow step `gh release edit v$VERSION --draft=false --latest` ([gh release edit](https://cli.github.com/manual/gh_release_edit); `gh` 2.103.3 ships on the macOS 26 arm64 image, [image readme](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md)). With `releaseType: "release"`, `createRelease` publishes first and uploads after, so `latest/download/...` would 404 for the upload window (read from source, not run). Draft-then-publish also fits immutable releases.
- **Asset names**: macros are `${productName}` (sanitized; ours has a space), `${name}` (`@repo/desktop` here), `${version}`, `${arch}`, `${os}`, `${platform}`, `${channel}`, `${ext}`, `${env.X}` ([file-patterns.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/file-patterns.md#file-macros)). Use a literal: `mac.artifactName: "Cube-Goblin-${arch}.${ext}"` gives `Cube-Goblin-arm64.dmg` and `Cube-Goblin-arm64.zip`. A user pattern applies to both targets and keeps `${arch}` even for the default arch (`artifactPatternConfig`, `platformPackager.js`). Names with characters GitHub rejects get a `safeArtifactName` rewritten into `latest-mac.yml` (`updateInfoBuilder.js`); a space-free literal avoids that.
- **Version-free names still work with the updater**: `latest-mac.yml` lists files by name, and `GitHubProvider` resolves each one to `/<owner>/<repo>/releases/download/<tag>/<name>` (`resolveFiles`, `getBaseDownloadPath`, checked in tarball). The tag disambiguates, so the same name in every release is fine.
- **Same-named assets**: names are per release, so v0.2.0 and v0.3.0 can both hold `Cube-Goblin-arm64.dmg`. Within one release, a 422 `already_exists` makes electron-builder delete the old asset and re-upload (`overwriteArtifact`); with immutable releases on, that fails once published.

## GitHub Actions (public repo)

- **Cost**: standard GitHub-hosted runners in public repos are free and don't draw down included usage; larger runners (`-large`, `-xlarge`) are billed even for public repos ([Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). Release assets have no bandwidth limit (above).
- **macOS arm64 labels** for public repos: `macos-latest`, `macos-15`, `macos-26` (3 M1 cores, 7 GB RAM, 14 GB SSD); `macos-15-intel` and `macos-26-intel` are x64 ([choose the runner](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/choose-the-runner-for-a-job)). `macos-latest` is macOS 26 arm64 today ([runner-images](https://github.com/actions/runner-images#available-images)); `-latest` migrations roll over 1-2 months, so pin `macos-26`. The image is macOS 26.7.2 with Node 24.22.2 ([image readme](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md)). macOS jobs may queue under high demand ([hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)).
- **Permissions**: `contents: write` "allows the action to create a release". Setting any permission sets the rest to `none` ([workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)). The token is referenced as `${{ secrets.GITHUB_TOKEN }}` ([GITHUB_TOKEN](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token)).
- **Tag trigger**: `on: push: tags: ['v*.*.*']`; patterns match `refs/tags/*` ([workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#example-including-branches-and-tags); electron-builder's own example uses `v*.*.*`, [github-actions.md](https://github.com/electron-userland/electron-builder/blob/electron-builder%4026.18.0/website/docs/features/github-actions.md)).
- **pnpm**: we pin `pnpm@10.8.1` in `packageManager`. `pnpm/setup` needs pnpm v11+, so use `pnpm/action-setup@v6` (latest v6.1.1, 2026-11-03) with `actions/setup-node@v7` (v7.1.0); `version` can be omitted when `packageManager` is set ([action-setup README](https://github.com/pnpm/action-setup/blob/v6.1.1/README.md)). Cache with action-setup's `cache: true` or setup-node's `cache: pnpm`; setup-node advises turning caching off in workflows with elevated privileges ([setup-node README](https://github.com/actions/setup-node/blob/v7.1.0/README.md)). pnpm's docs now lead with `pnpm/setup` ([pnpm CI](https://pnpm.io/continuous-integration#github-actions)), which needs the pnpm 11 upgrade first.

## electron-updater 6.8 check-only flow

- **No API, no token**: with no token and `private` unset, the factory picks `GitHubProvider` (`providerFactory.js`). It reads `github.com/<owner>/<repo>/releases.atom`, then `github.com/<owner>/<repo>/releases/latest` with `Accept: application/json` ("do not use API for GitHub to avoid limit"), then downloads `latest-mac.yml` from `/releases/download/<tag>/` (`GitHubProvider.js`, checked in tarball). Verified 2026-11-16: that `releases/latest` URL with JSON accept returns `{"tag_name": "v2.104.0", ...}` for `cli/cli`. Only `api.github.com` has the documented 60 requests/hour per IP unauthenticated limit ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)); the web endpoints have no published limit.
- **Prereleases**: `allowPrerelease` is false unless the running version has a prerelease part, so stable builds follow `releases/latest` (`AppUpdater.js`).
- **Check-only**: set `autoDownload = false` (default `true`); `checkForUpdates()` then emits `update-available` and returns `downloadPromise: null` (`doCheckForUpdates`, `AppUpdater.js`). It's a no-op unless `app.isPackaged` or `forceDevUpdateConfig` (dev reads `dev-app-update.yml`).
- **Payload**: `UpdateInfo` has `version`, `files[]` (`url`, `sha512`, `size`), `releaseName`, `releaseNotes` (string, or an array with `fullChangelog`), `releaseDate`, plus `tag` from the GitHub provider (`updateInfo.d.ts`, `GitHubProvider.js`). Open the share link rather than a `files` url, since it's the dmg we want.
- **Config source**: the build writes `app-update.yml` into the app's resources from the publish config (`PublishManager.js`), so the publish block also configures the updater. Don't call `setFeedURL` ([desktop-delivery.md](desktop-delivery.md#auto-update-electron-updater)).

## Rewriting the 16 commits' email

- **State (read-only, 2026-11-16)**: 807 commits across all refs; author and committer are `work-email` on 16 (all 2026-11-09, merges included), `himmelmax@gmail.com` on 791. None are signed (`%G?` is `N` on every commit; `commit.gpgsign` is `false`). No tags, 36 branches, two GitKraken refs (`refs/gitkraken/empty-tree`, `refs/worktree/gitkraken/undo`). `git-filter-repo` isn't installed. `appId` `com.maxhimmel.cube-goblin` is in tracked files, and the email only appears in the ticket.
- **Git's advice**: `git filter-branch` "has a plethora of pitfalls … its use is not recommended. Please use … git filter-repo" ([git-filter-branch](https://git-scm.com/docs/git-filter-branch#_warning)).
- **Usage**: write a mailmap line `Max Himmel <himmelmax@gmail.com> <work-email>`, then run `git filter-repo --mailmap <file>`. It rewrites author, committer, and tagger ([git-filter-repo docs](https://github.com/newren/git-filter-repo/blob/main/Documentation/git-filter-repo.txt), "User and email based filtering"). `--email-callback '<python body>'` is the scripted alternative.
- **Scope**: all refs. In a fresh clone it first turns `refs/remotes/origin/*` into local branches, removes `origin`, rewrites with `fast-export --all`, then runs `reset --hard`, `reflog expire --expire=now --all`, and `gc --prune=now`. Signatures get stripped, and abbreviated hashes in commit messages are rewritten (same doc, "INTERNALS" and "DESCRIPTION").
- **Fresh clone**: it aborts unless the repo looks like a fresh clone, and `--force` skips that check. The docs say clone with `git clone --no-local` for a local source ("DISCUSSION", "FRESH CLONE SAFETY CHECK").
- **Plan** (inferred, not run): run it in a `--no-local` clone under `/tmp`, never in this shared checkout. The `reset --hard` and reflog expiry would hit other sessions' worktrees and uncommitted work. Push the clone to the new GitHub repo, then re-clone or hard-reset local checkouts. The docs don't cover worktrees: branches merged or rebased onto the old `main` keep old hashes and must be rebuilt on the rewritten one (ticket's Decisions).
